# 09 现有知识点体系 × 外部 315 知识点整合规则

> 状态标记：**new**。复用 00–08 的审计与映射结论；不重复全仓审计。
> 数据版本：外部 `cf73951`；内部 62 个知识点（2026-10-25 只读快照）。
> 当前映射全部 `pending_review`，`confirmed=0`。

## 0. 节点分类（必须先区分）

| 类别 | 存放位置 | 是否进入内部树 | 说明 |
|---|---|---|---|
| 已有内部知识点 | `knowledge_points` | 是 | 62 个；ID 永久保留 |
| 外部知识点 | `taxonomy_external_topics` | 否 | 315 个初中节点 + 可选全量 |
| 已确认映射 | `taxonomy_topic_mappings`（`review_status=confirmed`） | 否 | 作为外部↔内部关系，不复制节点 |
| 待审核映射 | `taxonomy_topic_mappings`（`pending_review`） | 否 | 当前 12 条候选关系 |
| 待新增知识点 | 新增审核队列（`new_topic_pending`） | 审核通过后才进入 | 当前 303 个无候选节点 |
| 仅作目录组织的结构节点 | 外部 `domain/chapter` 元数据；内部 category | 内部 category 已在树中 | 章节默认不单独建内部节点 |

外部 ID（`cnm_001` 等）**只作为外部来源编码**，绝不替换或复用 `knowledge_points.id` / `slug`。

## 1. 外部六册结构如何对应现有树？

- 外部六册（7上 61、7下 58、8上 57、8下 57、9上 49、9下 33）是**教材组织元数据**，
  保存在外部节点字段 `grade` / `semester` / `chapter`，不直接变成内部树层级。
- 现有内部树是 `初三数学 → 7 个大类 → 54 个叶子`，表达的是知识主题，不是教材册次。
- 因此：**册次用于筛选/展示/审核上下文**；**章节默认只作为组织层级/标签**。
  只有经人工确认确有独立教学意义的章节，才考虑新增内部节点（本阶段不新增）。

## 2. 章节是否全部作为知识点树节点？

不。规则：
1. 外部 315 个正式知识点默认都作为**外部节点**保存；
2. 章节（948 个不同 chapter 值）只作为外部节点的属性/上下文，不批量建内部节点；
3. 如果某个章节本身是课程内容（如“综合与实践”活动），可由审核人将其作为一个外部节点处理，
   但仍需通过新增审核，不能自动建树；
4. 内部树只在“确认新增”时增加节点，且父节点必须显式指定。

## 3. 现有 62 个知识点如何保留？

- `knowledge_points.id` **永久保留**；正式导入不得 `rebuild`、清空或重建该表。
- 62 个节点继续承担：题目关联（`question_knowledge_points`）、向量检索（Chroma ID=`str(kp.id)`）、
  前端树与筛选。
- 外部映射只新增关联表记录，不修改 `name/slug/parent_id`。
- 若确需重命名/移动内部节点，走现有 CRUD 流程并单独审核，不能由外部导入自动覆盖。

## 4. 外部 315 个知识点如何与现有节点共存？

- 外部节点保存于 `taxonomy_external_topics`，内部节点保存在 `knowledge_points`；
- 通过 `taxonomy_topic_mappings` 建立“外部节点 → 内部节点”的候选/确认关系；
- 一个外部节点可以：
  - 对应一个内部节点（1-1）；
  - 对应多个内部节点（N-1 / 需要拆分内部节点）；
  - 无候选（303 个，进入新增审核）；
- 一个内部节点可以对应多个外部节点（1-N / 内部节点过粗，可能需要拆分）；
- 外部节点**不会**被复制成 315 个内部节点；只有人工确认“新增”的才进入内部树。

## 5. 一个外部知识点对应多个内部知识点时如何处理？

- 标记为 `many_to_one` 候选（外部 1 → 内部 N），流程状态设为 `needs_split`；
- **不得自动拆分内部节点**；
- 审核人选择：
  1. 确认其中一个内部节点为最佳匹配，其余作为“更细粒度”参考；
  2. 提出内部节点拆分方案（`needs_split`），走独立变更流程；
  3. 拒绝该外部节点或改为新增；
- 当前实际数据：N-1 分量为 0，暂无此类案例。

## 6. 多个外部知识点对应一个内部知识点时如何处理？

- 标记为 `one_to_many` 候选（内部 1 → 外部 N），流程状态设为 `needs_merge` 或保持 pending；
- **不得自动合并内部节点**；
- 审核人判断：外部节点是否确实都属于同一内部知识点；若是，可分别确认多个映射；
  若内部节点过粗，可提出拆分（`needs_split`）；
- 当前实际数据：1 个 1-N 分量（内部 `10 二元一次方程组` 对应 3 个外部节点），
  其中 2 个为高风险候选（`cnm_093`、`cnm_208`），已被排除在普通建议之外；
  排除后仅 `cnm_088` 可进入普通审核。

## 7. 无候选的 303 个节点如何进入人工新增审核？

- 统一进入 `new_topic_pending` 队列（见 `11_new_topic_review.md`）；
- 每个节点保存：外部 ID、名称、完整外部路径、册次、章节、课标引用、先修关系、
  新增建议、重复检查结果、审核状态与意见；
- 新增前必须检查：同义/近义、上下位、是否只是目录节点、是否重复、是否需拆分/合并；
- **必须人工确认**；原型不批量创建；
- 当前队列 303 个，其中 2 个存在近名内部候选（`duplicate_risk=medium`），需优先审核。

## 8. 如何避免重复创建知识点？

1. 外部节点唯一键 `(source_id, external_id)`；
2. 映射当前版本唯一（`mapping_key + current_flag`）；
3. 新增前在同一 `subject_id` 下做规范化名称与 bigram 近名检查（原型已实现）；
4. 禁止用外部 ID 作为 `knowledge_points.slug`；
5. 新增审批必须指定父节点，且检查同名/近名已有节点；
6. 已拒绝的新增/映射保留记录，重新推荐时默认跳过；
7. 批次执行幂等：相同决策重复执行不重复创建。

## 9. 先修关系与树的关系

- `parent_id` 只表达树形层级（分类/上下位），**禁止**写入先修关系；
- 先修关系独立保存：`topicId depends on prerequisiteId`，保留 hard/soft、来源、版本；
- 当前 563 条内部先修、45 条跨学段关系仅作为**候选投影**，未建立正式内部先修；
- 映射未确认时不得创建正式先修；映射后自环/重复/环必须进入冲突审核（见 12）。

## 10. 结论

315 个外部节点可以按“外部表 + 映射表 + 新增审核队列”的方式与现有 62 个内部节点共存；
无需重建内部树、无需复制外部节点、无需修改题目关联。所有正式关系必须经人工确认。
